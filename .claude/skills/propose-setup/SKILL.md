# Propose Setup

`agentsdir init` installs the architecture; this meta-skill fills it. Put
on the table the hooks, rules and sub-agents that would earn their place
in THIS repo — each with its reason and its evidence — and let the user
accept, refuse or amend them line by line. Nothing is written before every
line has an answer. Six steps, in order.

## 1. Inventory before proposing

- Read the facts the repo carries: the stack marker files and the commands
  they prove, the `package.json` scripts or their equivalent, the CI
  workflows under `.github/workflows/`, the linter and formatter configs,
  the test layout, AGENTS.md and the recent commit subjects. The Stack
  table of AGENTS.md already separates a proven command from a
  `_to fill in_` placeholder — keep that separation.
- Read what is already configured: `.agents/rules/`, `.agents/hooks/`,
  `.agents/agents/`, `.agents/skills/`, and the harness permission
  settings (.claude/settings.json). On a repo that already has rules or
  hooks the job is to COMPLETE that set: an element that duplicates one
  already there is never proposed, it is listed as already covered.
- Mark every fact `read` — naming the file it comes from — or `assumed`,
  when it is an inference from the stack conventions rather than something
  this repo states. Never propose an element resting on `assumed` facts
  alone: turn it into a question for step 2 instead.
- Check the current guidance before settling the proposal. Read the
  official documentation of the harnesses this repo enables (they are
  listed in `.agents.toml`) and of the model that will run it: what this
  kind of artifact is good for, and the fields it supports, move with
  them.
- PRIMARY sources only, whatever the medium: what the people who build
  that harness or that model publish themselves — their documentation,
  their talks and recorded sessions, their papers and slide decks. Never
  a third party's paraphrase of one.
- Note what you consulted and the date you consulted it, and say which of
  your choices it changed. An undated claim is an opinion, and the repo
  has enough of those already.
- No network access, or nothing found? Say so plainly and proceed on what
  the repo proves. A silent guess dressed as current practice is the one
  outcome worse than not looking.

## 2. Targeted interview

- Ask ONLY what the repo cannot answer. The bank is in
  references/interview.md: what the agents got wrong here, what is already
  enforced mechanically, which commands must never run, which step of the
  workflow is repeated by hand.
- Two or three questions, asked BEFORE the proposal is drafted — an
  interview run after the table only decorates a decision already taken.

## 3. Routing

- Qualify each need before it becomes a line: guaranteed on every event →
  hook; advisory knowledge that must be read in context → rule; bulky
  isolable work → sub-agent. An on-demand workflow is a skill, and skills
  are out of scope here — mention $create-skill and move on.
- No kind outranks another. A hook, a rule and a sub-agent each cover what
  the other two cannot, so the right mix is the one THIS repo and the
  user's request call for — the three together, one of them, or none at
  all. Rank the proposal by the strength of the evidence, never by the
  kind of artifact.
- EXCLUDE what a tool of this repo already enforces: a linter, a formatter,
  a type checker, a CI step, an existing hook, or a harness deny rule.
  A proposal never sends an agent to do a linter's job, and never writes a
  rule that restates a CI step: the rule drifts from the tool, and the tool
  wins.

## 4. Draft, then critique

- Draft the proposal as ONE table, one line per element: kind (hook, rule
  or sub-agent), name, why it is needed in THIS repo, the evidence with
  each fact marked read or assumed, and what it does not cover.
- Criticize every line with the filter
  question: "if this line is deleted, will the agent make a mistake?"
  Cut every element that fails it, and check the draft against every
  criterion of references/rubrique.md.
- Cut again: five founded elements beat fifteen generic ones. A list too
  long to read is accepted wholesale, then ignored — worse than an empty
  `.agents/`, because it looks configured.
- Present the table and ask for a verdict PER LINE: accept, refuse, or
  amend — and how. Record each refusal with its reason, so the same
  proposal does not come back. Write nothing until every line has its
  verdict.

## 5. Generate, then write

- Create the accepted lines only, one at a time, each through its own
  meta-skill: $create-hook for a hook, $create-rule for a rule,
  $create-agent for a sub-agent. Each of them runs its own inventory,
  interview and critique and calls the matching `agentsdir add` generator
  — do not replay their protocol here, and never write the files by hand.
- Carry the accepted line into the meta-skill as its starting material:
  its reason, its evidence and the amendments the user asked for. The
  creators ask what remains undecided; they do not restart the analysis.

## 6. Mechanical validation — mandatory

- Run `agentsdir check` once the accepted list is exhausted, and paste its
  passing output. Any deviation goes back to step 4 — never conclude on a
  failing check.
- Close with what was NOT created: the refused lines with their reason,
  and what a tool of the repo already covers. The user must be able to see
  that the proposal was complete and the omissions deliberate.
